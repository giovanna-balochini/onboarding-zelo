Onboarding técnico do Zelo

Apresentação navegável do produto, da arquitetura, das tecnologias e do estado atual do projeto — para quem está começando a contribuir no Zelo.

Seção 1

O que é o Zelo

O Zelo é um aplicativo mobile pensado para apoiar o cuidado da pessoa idosa sem reduzir esse cuidado a uma lista de tarefas. Ele combina rotina, comunicação e rede de apoio para que o idoso permaneça no centro da experiência, com mais autonomia, vínculo e previsibilidade no dia a dia.

Na prática, o produto tenta resolver um problema bem comum: informações importantes do cuidado costumam ficar espalhadas entre conversas, memória, agenda do celular e acompanhamento informal da família. O Zelo organiza esse cenário em uma experiência única, conectando idoso, responsável e rede de apoio em torno de uma rotina compartilhada.

Problema que o produto ataca

O cuidado da pessoa idosa raramente depende de uma única pessoa ou de um único lembrete. O desafio real é coordenar contatos, rotina, comunicação e acompanhamento sem perder clareza nem sobrecarregar quem cuida.

Quem participa da experiência

O produto envolve pelo menos três papéis: a pessoa idosa, o responsável principal e os contatos da rede de apoio. O fluxo de cadastro já reflete isso ao prever o registro do idoso e de um responsável desde o começo.

Como o cuidado é organizado

A rede de apoio funciona como a estrutura social do produto: é o conjunto de contatos que participa do cuidado. O idoso pode montar essa rede a partir da agenda do aparelho ou por inclusão manual, o que permite combinar praticidade e flexibilidade.

O que sustenta a proposta no app

Lembretes, notificações e assistência por voz entram como mecanismos para tornar a rotina mais acompanhável. O app trabalha com notificações locais no aparelho e também com notificações push via Firebase, para manter idoso e rede informados.

O Zelo não é só interface: ele depende de continuidade

O aplicativo Flutter não guarda sozinho as informações de cadastro, autenticação, rede de apoio e tokens de dispositivo. Esses dados precisam continuar existindo independentemente do aparelho, do login atual ou da tela aberta. Por isso o produto depende de uma API REST em Spring Boot e de integrações como Supabase, Firebase e WhatsApp. Essa camada técnica existe para sustentar a continuidade do cuidado, e não apenas para “salvar dados”.

Seção 3

Arquitetura e organização do código

Como o aplicativo e o backend se relacionam, e como o código está organizado em cada um dos lados.

Do app ao banco

  1. Flutter + Dart aplicativo mobile
  3. HTTP / JSON
  5. API REST — Spring Boot ponto de entrada
  7. Controllers recebem a requisição e validam o DTO
  9. Services regras de negócio
  11. Repositories / JPA acesso aos dados
  13. PostgreSQL persistência relacional

Integrações externas

Cada integração se conecta em um ponto diferente do fluxo — não passam todas pelo mesmo caminho.

  • Supabase Auth Backend → Supabase (autenticação)
  • WAHA Backend ↔ WhatsApp (webhook e envio de link)
  • Firebase Admin SDK Backend → Firebase (envio de push)
  • Firebase Cloud Messaging Firebase → App (recebimento de push)

Os Controllers recebem a requisição HTTP, validam o DTO de entrada e delegam ao Service, que concentra as regras de negócio. O acesso ao banco acontece pelos Repositories (Spring Data JPA). As entidades são o que é persistido no PostgreSQL; os DTOs e os mappers fazem a conversão entre o mundo HTTP e o mundo persistente, conforme a implementação.

Contrato de resposta — ApiResponseDTO

As respostas da API seguem um envelope comum, com os campos success, message e data. O campo data é omitido quando não há conteúdo. 

{
  "success": true,
  "message": "Token do dispositivo salvo com sucesso.",
  "data": null
}
Seção 4

Design System ZDS v1.0

O Zelo tem um Design System próprio, o ZDS v1.0. Ele define cores, tipografia, espaçamento, movimento e componentes para manter a consistência visual, permitir a reutilização e concentrar as decisões de acessibilidade em um só lugar.

Identidade visual

Verde Zelo #0F4C3A Cor primária — ações e marca.
Terracota #E27355 Acento. Não usar como texto nem ícone sobre fundo claro (2.92:1).
Creme Acolher #FDF8F2 Cor de fundo das telas.

O app usa tema claro e Material 3. A tipografia é a Plus Jakarta Sans, incluída nos assets do projeto — por isso funciona offline, sem depender de fonte externa.

Tokens

Os tokens são os valores visuais do sistema, definidos uma única vez e reaproveitados pelos componentes.

Cores

Paleta da marca e neutros.

Cores semânticas

Papéis de cor: sucesso, alerta e erro.

Tipografia

Família, pesos e escala de texto.

Espaçamentos

Escala com base em 4, de xs a giant.

Bordas e raios

Escala discreta de raios, de sm a full.

Elevação

Sombras em duas camadas (raised e overlay).

Alvos de toque

Tamanho mínimo e tamanho de ação das áreas clicáveis.

Ícones

Tamanhos e rótulos semânticos em português.

Assets

Caminhos de arquivos, como a logo do topo.

Movimento

Durações e curvas, respeitando a preferência por reduzir animações.

Os 11 itens acima são os componentes genéricos do Design System. Componentes específicos de uma funcionalidade — como uma tela ou um card próprio — ficam junto da funcionalidade em lib/ui/, e não dentro do Design System.

Regras de uso

  • Usar o tema e as cores semânticas; evitar cores e estilos literais no código.
  • Reutilizar componentes do Design System em vez de recriar equivalentes.
  • Manter a consistência tipográfica — família, pesos e escala.
  • Respeitar os alvos de toque mínimos definidos nos tokens.
  • Prever a ampliação de texto sem quebrar o layout.
  • Respeitar a preferência do sistema por reduzir animações.

Acessibilidade

O ZDS adota a WCAG 2.2 como referência, com contraste de 7:1 para texto (nível AAA) e alvos de toque de pelo menos 48dp. São requisitos adotados no projeto — e não uma garantia de que toda tela já esteja em conformidade.

Não verificado Situação dos testes. A documentação de origem cita cerca de 132 testes de contrato dos componentes e 13 testes de cadastro. No repositório atual existe apenas test/widget_test.dart, então esses números não puderam ser confirmados. Esse único teste espera o texto "Olá", enquanto a tela inicial renderiza "Zelo App" — ou seja, ele está desatualizado.

Seção 6

Segurança

O projeto adota cuidados explícitos para proteger o fluxo de autenticação e os dados sensíveis. Os pontos abaixo foram conferidos no código do backend.

OTP cifrado em repouso

O código OTP do fluxo é guardado cifrado com AES-256-GCM (AES/GCM/NoPadding). Cada operação usa um IV aleatório de 12 bytes e o id do fluxo entra como dado autenticado (AAD) — o que impede reaproveitar o texto cifrado em outro fluxo.

Telefone protegido por HMAC

O telefone não é consultado em texto puro. O backend calcula um HMAC-SHA256 com chave e usa esse valor nas buscas e nos limites por telefone.

Token do link guardado como hash

O token entregue no link não é armazenado em claro. O backend guarda apenas o SHA-256 dele e localiza o fluxo por esse hash.

Comparação em tempo constante

As comparações de segredo usam MessageDigest.isEqual, que evita vazar informação pelo tempo de resposta da comparação.

Assinatura HMAC do webhook

O webhook de envio de SMS é validado com HMAC-SHA256 no formato id.timestamp.corpo. A verificação limita o tamanho do corpo e dos campos e exige uma janela de tempo de até 5 minutos.

Expiração e limites

O link expira em um intervalo curto — entre 60 e 300 segundos, validado na configuração. Há limite de tentativas por fluxo, de reenvios, de intervalo entre reenvios e de fluxos por telefone a cada hora.

Token de acesso e rotas

O JWT é validado localmente com ES256 a partir do JWKS, e o emissor é conferido. As rotas públicas são explícitas: confirmação de usuário, fluxos de autenticação, login e o webhook. Qualquer outra rota exige autenticação.

Configuração validada. Os valores de expiração e de limites têm faixas permitidas e são verificados na inicialização — uma configuração fora da faixa impede a aplicação de subir, em vez de gerar um comportamento inseguro silencioso.

Seção 7

Um retrato do que já está pronto e do que ainda falta, olhando os dois repositórios.

No backend, cadastro, autenticação por WhatsApp, rede de apoio, periodicidade/horários e tokens de dispositivo estão implementados. No aplicativo, o Design System e as telas de cadastro e de rede de apoio estão montados, mas a ligação com a API ainda não está ativa ponta a ponta.

  • Pendente
    Enviar o token FCM ao backend

    O app obtém o token, mas apenas o imprime no console. O endpoint POST /api/device-tokens já existe e está pronto para receber.

    Usar a API real na rede de apoio

    O app injeta RedeApoioRepositoryFake. É preciso trocar pelo repositório real e alinhar o caminho: o app usa /api/v1/rede-apoio, e o backend expõe /api/rede-apoio.

  • Pendente
    Tela de login por WhatsApp

    Os fluxos, o login e o webhook existem no backend; falta a tela correspondente no aplicativo.

  • Pendente

    Os endpoints estão prontos; não há telas no aplicativo.

  • Pendente
    Concluir a confirmação de conta

  • Pendente
    Home

Seção 8

Setup rápido

O caminho mais curto para subir backend e aplicativo na sua máquina. Os comandos abaixo refletem o que está nos repositórios hoje.

Você precisa de Java 25, do wrapper Maven (já incluído como mvnw), do Flutter e do Docker. O backend lê a configuração de um arquivo .env na raiz; o aplicativo lê o endereço da API de lib/config/api_config.dart.

Backend — Spring Boot

  1. Suba o PostgreSQL do projeto (container zelo_postgres, banco zelo). 
    docker compose up -d
  2. Crie um .env na raiz com as chaves exigidas na inicialização. 
    AUTH_LINK_BASE_URL=https://...
AUTH_TOKEN_ENCRYPTION_KEY=32 bytes em Base64
SUPABASE_URL=https://SEU-PROJETO.supabase.co
SUPABASE_ANON_KEY=...
SUPABASE_WEBHOOK_SECRET=...
FIREBASE_CREDENTIALS_PATH=./serviceAccount.json
WAHA_BASE_URL=...
WAHA_API_KEY=...
  3. Suba a aplicação. 
    ./mvnw spring-boot:run
  4. Confira a documentação viva em /swagger-ui/index.html.

App — Flutter

  1. Baixe as dependências. 
    flutter pub get
  2. Rode a análise estática antes de executar. 
    flutter analyze
  3. Execute no dispositivo ou emulador. 
    flutter run
  4. Confira o endereço da API em api_config.dart: 10.0.2.2 é o host visto de dentro do emulador Android; localhost vale para desktop e iOS.

Duas divergências para alinhar antes de rodar

O docker-compose.yml publica o PostgreSQL na porta 5433, mas o application.yaml aponta para 5432. E o RedeApoioController expõe /api/rede-apoio, enquanto o README e o aplicativo usam /api/v1/rede-apoio. Ajuste um dos lados antes de testar a integração.

Segredos fora do repositório. O .env e o arquivo de credenciais do Firebase não devem ser versionados. O application.yaml apenas referencia as variáveis — nenhum valor sensível fica no código.
